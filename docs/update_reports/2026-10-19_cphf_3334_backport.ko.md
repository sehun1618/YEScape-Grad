# CPHF/UCPHF 조기 종료: PySCF #3334 로컬 반영과 검증

작성일: 2026-10-19 (KST). 기준 commit: `333ad3f332aaab12bfbe8efb33e37819b73ccdd3`.

## 결론

CPU/GPU 분자계 RHF/UHF와 Gamma PBC의 CPHF 호출에 #3334의 임계값 처리를
명시적으로 반영했다. **왜곡 CH₂에서 잔차가 약 9.3배 감소했고 FD 일치도도
개선됐다. 그러나 OH 잔차는 줄지 않았다. 모든 물질에서 요청 tolerance까지
수렴한다고 주장할 수 없다.** 기존 physical residual 검사·경고·fallback은 유지했다.

이 변경은 설치된 PySCF/GPU4PySCF 자체를 수정하지 않는다. 실행 중인 Water64
SOSCF를 보호하기 위해 별도 Git worktree에서 검증했다. 원본 checkout은 계산
종료 후 fast-forward하도록 보류한다. 기존 v6 결과를 수정하거나 재계산하지 않았다.

## 1. 어떤 문제를 고쳤는가

설치된 PySCF 2.14.0 / GPU4PySCF 1.8.1의 CPHF는 Krylov 기본값
`lindep=1e-13`을 사용한다. 이 값은 벡터 노름의 **제곱**과 비교된다.
따라서 `tol=1e-12`라고 해도 작은 Krylov 방향을 먼저 버리며 종료할 수 있다.

[PySCF PR #3334](https://github.com/pyscf/pyscf/pull/3334)는 다음을 바꾼다.

1. CPHF/UCPHF에서 `lindep=max(tol**2, eps(real_dtype))`를 전달한다.
2. CPU Krylov의 초기 QR와 반복 중 QR에도 그 `lindep`를 전달한다.

FP64에서 `tol=1e-12`이면 `lindep=2.220446049250313e-16`이다.
`tol**2=1e-24`까지 낮추는 수정이 아니다. 실제 physical residual은 orbital
energy denominator와 Hessian 조건수에도 영향을 받는다. 따라서 이 변경 뒤에도
`max|H Z - F_vo| > tol`인 경우가 남는다. 이 residual은 **force 오차와 다르다**.

GPU Krylov는 이미 두 `_stable_qr`에 `lindep`를 전달한다. GPU에는 CPHF/UCPHF에서
전달하는 임계값을 고치는 부분이 필요했다. 같은 방향의 upstream 변경은
[GPU4PySCF PR #951](https://github.com/pyscf/gpu4pyscf/pull/951)에도 있다
(2026-10-13 병합; 설치된 1.8.1에는 미포함).

## 2. 구현 범위와 재사용 방식

- 공통 호환 함수: `dcforge/tools/cphf.py:solve`.
- CPU/GPU `grad/rhf_zvec.py`, `grad/uhf_zvec.py`의 모든 CPHF/UCPHF 호출.
  UHF에서 한 spin의 VO 공간이 비어 CPHF로 내려가는 두 분기도 포함한다.
- CPU/GPU `pbc/grad/rhf_zvec.py`의 primary CPHF 호출.
- `s1=None`, `s1!=None`, 단일/다중 RHS에 동일 정책을 사용한다.

CPHF 식을 복사해 재구현하지 않고 **설치된 함수 본문을 그대로 실행**한다.
`FunctionType`으로 해당 호출에 한정된 private globals를 연결하여 Krylov 인자와
CPU QR의 default만 교체한다. 전역 monkeypatch를 하지 않으므로 동시에 다른
tolerance로 호출해도 서로의 설정을 덮어쓰지 않는다. 별도 의존성은 없다.

다음은 변경하지 않았다.

- HF SCF, upstream SOSCF, site-packages, 의존성 버전.
- sampled-k 자체 solver, 큰 GPU Gamma 공간의 MINRES/GMRES, 별도 mixed-Z3.
- CPU Gamma의 기존 더 엄격한 Krylov residual fallback 및 bounded dense fallback.
- physical residual의 허용값, 경고만 하는 분자계 정책, gradient 부호와 수식.

**Water64 v6의 별도 mixed-Z3가 이 수정으로 자동 개선됐다는 뜻은 아니다.**
전체 Python 지문은 달라지므로 기존 runner의 source identity 정책은 별개로 고려해야 한다.

## 3. 실제 분자 검증

환경: conda `gpu`, PySCF 2.14.0, GPU4PySCF 1.8.1, CuPy 14.0.1,
RTX PRO 6000 Blackwell Server Edition. GPU 테스트는 cuTENSOR 활성화를 확인했다.
GPU에서는 기존 SOSCF와 장치를 공유했다. 아래 결과는 **정확성 검증**이며,
JSON의 wall time을 독립적인 속도 비교로 사용하면 안 된다.

조건: PBE@HF, STO-3G, source `conv_tol=1e-11`, `conv_tol_grad=1e-9`,
CPHF `tol=1e-12`. 분자와 방법별로 **같은 수렴 HF 상태**에서 native/backport
gradient를 구했다. FD에서는 양쪽 변위의 HF를 새로 수렴시켰다.
물과 CH₂는 grids level 3, OH는 4, prune=None. 재현성을 위해 CPU는 1 thread.
DF는 PySCF matching default auxbasis. 아래 FD는 H 원자(index 1)의 z 성분이다.
변위는 물/CH₂ `1e-4 Bohr`, OH `2e-3 Bohr`.

## 4. 회귀 검사와 알려진 한계

`tests/unit/test_cphf_3334.py`는 다음을 확인한다.

- 작은 단일 RHS와 거의 평행한 두 RHS를 dense diagonal solution과 비교.
- RHF/UHF, CPU/GPU, overlap 유/무, level shift 및 한 spin만 활성인 UHF 분기.
- float32/float64/complex64/complex128의 real-dtype epsilon 선택.
- 서로 다른 tolerance의 동시 호출, 전역 solver 불변, 잘못된 tolerance 거부.

작은 RHS witness에서는 native residual `3e-8`이 수정 후 수치적으로 0에 도달했다.
이것은 통제된 1차원 검사이지 모든 분자에 대한 보장은 아니다.

GPU4PySCF 1.8.1의 restricted `s1=None, level_shift!=0`에는 별도의 2D/3D
broadcasting 오류가 있다. 두 검사에서 **native에서도 오류가 나는지 확인한 뒤**
expected failure로 표시했다. 현재 DC-Forge Z 호출의 level shift는 0이며 영향받지
않는다. 이 문제까지 수정한 것으로 오해하면 안 된다. 업그레이드 때 다시 검사한다.

새 worktree에는 처음에 PBC C extension이 없어서 GDF 검사가 import 실패했다.
`python setup.py build_ext --inplace`로 그 worktree 안에서 빌드해 해결했다.
원본 checkout의 binary나 설치 환경은 변경하지 않았다.

최종 회귀 명령과 결과는 아래 검증 완료 항목에 기록했다.

## 5. PySCF 2.15 / GPU4PySCF 업데이트 체크리스트

버전 번호만 보고 호환 함수를 삭제하거나 새 기능을 중복 backport하지 않는다.

1. 실제 설치된 tag/wheel과 함수 소스를 확인한다.
2. CPU CPHF/UCPHF의 `solve_nos1`, `solve_withs1` 네 경로에서 adaptive `lindep`를 확인한다.
3. CPU `lib.linalg_helper.krylov`의 **두 QR 호출 모두** 전달받은 `lindep`를 쓰는지 확인한다.
4. GPU4PySCF CPHF/UCPHF 네 경로는 독립적으로 확인한다. PySCF만 업그레이드해도
   GPU solver가 바뀌는 것은 아니다. #951의 최종 릴리스 포함 여부를 확인한다.
5. 새 환경에서 native와 이 호환 함수의 small/near-dependent RHS 결과를 비교한다.
   분자 RHF/UHF conventional/DF, Gamma FFTDF/GDF, selected FD까지 재검증한다.
6. 검증된 backend만 native 호출로 되돌린다. GPU가 미수정이면 GPU 호환 경로는 남긴다.
7. native가 explicit QR `lindep`를 전달하는 경우 이 호환 함수도 그 값을 그대로
   수용한다. 두 번 solve하지는 않는다. 다만 검증 후 불필요한 호환 코드는 제거한다.
8. **physical residual 검사와 기존 fallback은 제거하지 않는다.** 이번 OH 결과가
   보여 주듯 upstream 수정은 residual 보증을 대체하지 못한다.

기존 2026-10-13 업그레이드 보고서와 연결해 검토하되, 그 당시 draft source 감사와
이번 **설치된 2.14.0/1.8.1의 실제 계산**을 혼동하지 않는다.

provenance JSON과 두 commit의 `dcforge/` tar.gz를 보존했다.

|---|---:|
| `e133fee6f0787e2accf6b055440e232230e8d424` | 248 |
| `333ad3f332aaab12bfbe8efb33e37819b73ccdd3` | 1,337 |

합계 1,585개 = 일반 v6 1,583개 + extreme SOSCF 2개. 2026-10-19 기록 시점의
snapshot이다. 두 commit의 Git blob으로 재계산한 Python 지문이 각 완료 결과의
저장 지문과 일치한다. `dirty=true`만으로 source가 불명확하다고 처리하지 않았다.
이 일치는 runner/외부 의존성까지 증명하는 것은 아니므로 해당 지문도 CSV에 남겼다.

원본 저장소의 실행 중 Python 파일은 그대로 유지한다. 별도 worktree에서
commit/push한 뒤, SOSCF parent queue까지 모두 종료된 것을 확인한 다음에만
원본 저장소에서 `git merge --ff-only origin/main`을 수행한다. 진행 중에는 금지한다.
